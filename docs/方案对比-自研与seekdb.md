# 自研方案 vs seekdb — 对比分析

> 状态：已拍板选**自研**（2026-03-25；2026-08 判决定案纯余弦，取消加权融合）  
> 需求原文：[需求说明](./需求.md)  
> 对照官方：seekdb 1.3.0 文档（[pyseekdb 快速开始](https://docs.seekdb.ai/seekdb/pyseekdb-sdk-get-started)、[官网](https://www.seekdb.ai/)）

---

## 1. 结论

万级、单文件查重、Windows 单 exe 这个场景，**自研在质量、耗时、落地成本上都优于 seekdb**。

seekdb 适合「会长大的持久知识库 + 在线混合检索」。本工具是「对这一份表算一次，关掉就丢」。能力清单好看，不等于匹配工作负载。

「自己写余弦」实际是几十行代码，换不来一个数据库引擎的打包与平台成本。

---

## 2. 两种方案分别是什么

### 2.1 自研（已选）

```
读 Excel
  → 汉字 2/3-gram + BM25（必开）
  → 可选：远程 Ollama / vLLM 批量 embedding
  → numpy 分块精确余弦，每题 Top50
  → 候选 = BM25 Top50 ∪ 向量 Top50；判决纯余弦（无向量时纯 BM25）
  → 分数留内存，滑条只过滤
  → 导出题对
```

不落库、不打包模型、不上 ANN / 向量库。打包：Python + PyInstaller onefile + CustomTkinter。

### 2.2 seekdb

OceanBase 的 AI 原生搜索库：向量 + 全文 BM25 + SQL + `DBMS_HYBRID_SEARCH`（加权 / RRF）。可嵌入（pip）或独立服务。设计目标是 RAG / Agent / 持久知识库，不是一次性全表互查。

---

## 3. 先决条件：Windows 嵌不进 exe

官方 1.3.0：

| 系统 | 嵌入式 | 服务端 |
|---|---|---|
| Linux | 支持 | 支持 |
| macOS | 支持 | 支持 |
| **Windows** | **尚未支持** | 支持 |

本工具目标是 Windows 便携 exe。选 seekdb 只能再挂 **server 进程**（独立服务 + 端口 + 数据目录），不再是「一个 exe 随时用」。体积、杀毒、权限、冷启动都会明显变差。这是官方平台能力，不是实现细节。

嵌入式安装前提（Linux）：glibc ≥ 2.28，Python ≥ 3.11。与「拷走就能用」不是同一类交付。

---

## 4. 比较质量

两边若接入**同一个** Ollama / vLLM 模型，向量本身没差别。差别在怎么比、怎么判决、分数能不能留下来改阈值。

| 维度 | 自研 | seekdb | 对本需求 |
|---|---|---|---|
| 向量比较 | 精确余弦（`X @ X.T`） | 默认 HNSW，**近似**；也可精确 | 查重怕漏检，万级没必要近似 |
| BM25 分词 | 字 2/3-gram | Space / Beng / Ngram / IK / Jieba | 近重复时字 n-gram 往往比 jieba 稳（换说法会切得不一样） |
| 判决 | 纯余弦（实测掺 BM25 任何比例都减分，混合已取消） | 官方 hybrid + RRF / 加权 / LLM rerank | 66 题实测：任何模型掺入都掉命中；纯余弦更可解释 |
| 阈值重调 | 全量候选分在内存，滑条即滤 | API 偏「查 1 条返回 Top-K」 | 改阈值再查会打到用户最怕的点 |
| 内置 embedding | 无，强制走用户模型或纯 BM25 | 默认常见为 `all-MiniLM-L6-v2`（英文 384 维） | 中文试题走内置模型会伤质量；中文语义两边都得接远程模型 |

**本场景质量：自研略优。** 原因是精确全比 + 分数常驻，而不是「库更成熟所以更准」。

---

## 5. 比较耗时

本机（用户机器）已测：768 维 float32，分块精确余弦 + 每题 Top50。

| 题量 | 自研余弦 | 说明 |
|---|---|---|
| 1 万 | **1.3 s** | 向量 31 MB，结果 4 MB |
| 3 万 | **5.7 s** | 向量 92 MB，结果 12 MB |

1 万题时间账：

```
读表 + BM25              < 5 s          两边同量级（seekdb 还要建全文/HNSW 索引）
远程 embedding           1～10 min      谁都省不掉
向量近邻                 自研 ~1.3 s    seekdb = 循环 n 次 hybrid（通常更慢）
收集候选并集             < 0.01 s       可忽略
改阈值                   自研即时       seekdb 易变成再查一遍
引擎冷启动               无             server 模式数秒～数十秒
```

向量库快，是因为「百万库里查 1 条」。本需求是「1 万条自己和自己比」——批处理全比较，BLAS 矩阵乘比 n 次 HNSW 更合适，且是精确结果。

**本场景耗时：自研更快。** 共同大头仍是远程向量化。

## 6. 比较可扩展性

| 以后若变成… | 更合适的一方 |
|---|---|
| Excel 到 3～5 万，仍是单次查重 | 自研（分块 Top-K 即可） |
| 10 万+ 仍要精确互查 | 自研会到分钟级；换 ANN 实现，不必换整库 |
| **持久题库 + 边录边查 + 多用户 + SQL 过滤** | **seekdb 明显更优** |
| 增量写入、事务、JSON 元数据 | seekdb |

需求已明确：**不落库**。SQL、OLTP、GIS、库内推理对本期是闲置能力。为用不到的扩展性先背一个引擎，是过早抽象。

接口上预留 `build / search / fuse` 即可。真做成常驻题库服务时再换 seekdb，不必现在绑死。

---

## 7. 「一劳永逸」拆开看

| 以为 seekdb 能省掉的 | 实际 |
|---|---|
| 自己算余弦 | `X @ X.T` + 分块 Top-K，几十行；万级 1.3 秒 |
| 自己做融合 | 已不需要（判决纯余弦）；seekdb 内部是加权 / RRF |
| 中文语义 | 内置英文小模型不适用；仍要接 Ollama / vLLM |
| Windows 单 exe | 嵌入式官方未支持，只能打成「exe + 数据库服务」 |
| 改阈值不重算 | 不是库的默认用法，还得自己把分数捞出来缓存 |

省下的不是架构，是约 80 行代码。换来的是平台限制、体积和近似检索。

---

## 8. 产品匹配度

| 需求特征 | 自研 | seekdb |
|---|---|---|
| 单文件内部互查 | 一次建、一次全比 | 为「1 query vs 库」设计，互查要循环 n 次 |
| 不持久化试题 | 内存即可 | 落盘引擎是它的主场，这里用不上 |
| 阈值滑条反复滤 | 分数自持 | 要额外做结果缓存才等价 |
| 无模型回退 BM25 | 自然降级 | 也能只开全文，但引擎仍在 |
| 单文件便携 | 几十 MB 级 exe | Windows 需附带 server |
| 以后变题库平台 | 要重做存储层 | 这才是它的主场 |

---

## 9. 决策与复评条件

**本期采用自研，不上 seekdb。**

只有同时出现下面多数条件，才值得复评 seekdb（或同类引擎）：

1. 产品改为常驻题库，试题要落盘、增量更新
2. 交互改为「录一道 / 查一道」，而不是整表互查
3. 需要 SQL 过滤、多用户、事务
4. 规模到十万～百万，且接受近似近邻
5. Windows 嵌入式被官方支持，或交付形态改为「本地服务」而不再是单 exe

复评时仍建议：**中文 embedding 继续走用户的 Ollama / vLLM**，不要用库内英文默认模型做试题查重。
